# ballast

**ballast는 긴 세션의 표류를 막는 Claude Code 플러그인이에요. 정해둔 상시 규칙은 걸리는 메시지마다 함께 도착하고, 한번 내린 결정은 원장(덧붙이기만 하고 고쳐 쓰지 않는 결정 기록부)에 잠겨요.**

구성은 마크다운 스킬들과 의존성 없는 스크립트 하나가 전부예요. 설치는 명령 두 줄이고, 요구사항은 `node` 18 이상 하나뿐이에요. 그리고 빈 채로 출발해요: 규칙 카탈로그(규칙을 모아두는 파일)에 규칙이 들어오기 전까지 훅(메시지를 보낼 때마다 자동으로 도는 스크립트)은 조용하고, 규칙을 넣는 방법이 아래 빠른 시작이에요.

세션에서는 이런 모습이에요:

> **사용자:** "저 싼 모델도 괜찮아 보이는데 — 그냥 그걸로 바꿔줘"
> **rules hook** *(메시지와 함께, Claude가 답하기 전에 배달)*: "사용자가 고정한 것을 임의로 바꾸지 않는다. 먼저 `memory/DECISIONS.md`를 확인한다. 제안만 하고, 결정은 사용자가 한다."
> **Claude:** "이 모델은 8월 13일에 고정해 두셨어요 — 원장의 D-012 항목이에요. 비교표를 드릴게요. 결정은 직접 하시면 돼요."

ballast가 보장하는 부분은 가운데 줄이에요. "바꿔"라는 말이 규칙 하나에 걸렸고, 그래서 규칙 본문 전체가 메시지와 함께 도착했어요 — Claude가 기억해 낼 필요가 없어요. 마지막 줄은 Claude가 건네받은 규칙을 따른 결과예요. 원장을 펼친 건 규칙이 시켜서지, D-012를 스스로 떠올려서가 아니에요.

## 설치

```
/plugin marketplace add svy04/ballast
/plugin install ballast@ballast
```

훅은 PATH에 이미 있는 `node`(18 이상)로 돌아가요. 나머지는 전부 마크다운이에요.

## 왜 ballast인가

아래 표에서 *코드*는 스크립트가 강제한다는 뜻이고, *규약*은 Claude가 따르기로 한 마크다운 지침이라는 뜻이에요.

| 문제 | 증상 | 처방 |
|---|---|---|
| `CLAUDE.md`는 한 번 읽히고 끝 — 긴 세션은 점점 멀어져요 | 같은 교정을 세션마다 반복 | **rules hook** *(코드)* — 걸리는 규칙의 본문 전체를 메시지마다 배달해요 |
| 결정이 지난 대화 속에 묻혀요 | 끝난 논의가 다시 열리거나, 슬쩍 고쳐짐 | **decision ledger(결정 원장)** *(규약)* — 덧붙이기만 돼요. 번복은 대체(supersede) 기록으로 남겨요 |
| 그럴듯한 문장이 사실로 굳어요 | 검증 안 된 주장 위에 선 자신만만한 답 | **verify gate(검증 관문)** *(규약)* — 모든 주장에 라벨이 붙고, `confirmed`(확인됨)는 얻어내야 해요 |
| 카피가 제품이 아니라 로드맵을 설명해요 | 없는 기능을 두고 "우리는 X를 해요" | **proof standard(증거 기준)** *(규약)* — 대외 주장은 진실 파일에서만 나와요. 진실 파일은 제품이 검증 가능하게 하는 일을 증거와 함께 적어둔 기록이에요 |
| "완료"의 근거가 Claude의 말뿐이에요 | 선언된 성공, 조용한 실패 | **goal** *(규약)* — 완료 = 검사 통과예요. 파일이 있고, 테스트가 돌고, 산출물을 실제로 봤을 때만요 |

다섯 줄 중 코드로 강제되는 건 한 줄이에요. rules hook은 프롬프트마다 실행되는 스크립트라, Claude가 협조하든 말든 발동해요. 나머지 넷은 규약이에요. Claude가 따라 주는 만큼만 지켜지니, 여느 프롬프트처럼 흐려질 수 있어요. ballast는 이걸 아닌 척하지 않아요. 대신 규약을 강제로 끌어올리는 통로를 둬요 — **pin**이에요. 규약이 미끄러지면 한 번만 교정하세요. pin이 그 교정을 규칙 카탈로그에 적고, 그다음부터는 훅이 배달해요.

## 무엇이 달라지나

| 이전 | 이후 |
|---|---|
| 같은 교정을 매주 반복해요 | **pin**이 한 번 적어두면, 걸리는 메시지마다 같이 도착해요 |
| 상시 규칙이 관련이 있든 없든 컨텍스트를 차지해요 | 걸린 규칙만 배달돼요 — 상한은 12개·약 6,000자(훅 소스에 고정된 값) |
| 세웠어야 할 프롬프트가 그냥 통과해요 | `action: "block"`이 걸린 프롬프트를 거절하고, 그 규칙을 사유로 보여줘요 — 가드레일이지 샌드박스는 아니에요(훅이 못 돌면 차단도 꺼지는 fail-open — 자세한 건 빠른 시작) |
| 세션이 바뀌면 기억이 초기화돼요 | `memory/` 파일이 남아요: 인덱스, 원장, 미해결 질문, 세션 로그 |

## 구성 조각

| 조각 | 종류 | 역할 |
|---|---|---|
| **rules hook** | 코드 — 프롬프트마다 도는 스크립트 | 걸리는 규칙 전부를 본문 그대로, 작업이 시작되기 전에 메시지와 함께 배달해요. `action: "block"`이 붙은 규칙은 배달 대신 프롬프트를 세워요 |
| **decision-ledger** | 규약 — 마크다운 스킬 | 덧붙이기만 되는 `DECISIONS.md`를 지켜요. 마음이 바뀌면 대체 링크를 남기지, 조용히 고치지 않아요 |
| **verify-gate** | 규약 — 마크다운 스킬 | 조사 결과와 모델 지식은 초안 취급이에요 — 반박 시도를 견디고, 출처 이름을 대고, 라벨(`confirmed` 확인됨 / `observed` 관찰됨 / `assumed` 가정 / `hearsay` 전언 / `unknown` 모름)을 달기 전까지요 |
| **proof-standard** | 규약 — 마크다운 스킬 | 진실 파일에 증거가 없으면 제품에 대한 대외 주장을 못 해요. 코드는 4단계(구현됨·연결됨·가동 중·검증됨)로 추적하고, 카피가 그 경계를 흐리면 안 돼요 |
| **brain-init** | 규약 — 마크다운 스킬 | 기억 구조의 골격을 깔아요: 인덱스, 원장, 미해결 질문, 세션 로그, 제품 진실 |
| **goal** | 규약 — 마크다운 스킬 | 감으로 밀기엔 너무 크거나 낯선 목표를 받아요. 그 분야의 쟁점과 초심자 함정부터 지도로 그리고, 목표를 하나씩 검증할 수 있는 크기로 쪼개고, 검사를 통과하기 전엔 아무것도 완료라고 부르지 않아요 |
| **pin** | 규약 — 훅이 강제할 규칙을 써요 | 방금 받은 교정을 한 번에 영구 규칙으로 바꿔요 |

## 빠른 시작

1. 아무 일에서든 Claude를 한 번 교정해 보세요. 교정이 곧 **pin** 스킬의 신호예요. Claude가 규칙 초안을 만들어 보여주고, OK 하면 카탈로그에 적어요 — 그때부터 걸리는 메시지마다 같이 도착해요.
2. `/ballast:brain-init` — 프로젝트에 기억 파일의 골격을 깔아요.
3. `/ballast:goal <큰 목표>` — 전체 파이프라인을 돌려요. 낯선 분야라면 답을 하나라도 내놓기 전에, 그 분야에서 무엇이 논쟁 중이고 무엇이 정설이고 초심자가 어디서 데는지부터 지도로 그려요.

규칙은 `<프로젝트>/.claude/ballast.rules.json`과 `~/.claude/ballast.rules.json`에 있어요(`id`가 겹치면 프로젝트 쪽이 이겨요):

```json
{
  "id": "cost-gate",
  "title": "Estimate before spending",
  "when": { "keywords": ["generate", "credits"], "patterns": ["\\bbatch\\b"] },
  "action": "inject",
  "body": "Anything that spends money: estimate first, explicit approval, then execute."
}
```

`keywords`는 대소문자 구분 없는 부분일치로, `patterns`는 정규식으로 걸려요. `always: true`는 매 메시지에 발동해요 — 1~2개로 아껴 쓰세요. `action: "block"`은 프롬프트를 세우고 `body`를 사유로 보여줘요. `BALLAST_DISABLE=1`이면 훅이 꺼져요.

기대기 전에 알아둘 설계 사실이 두 가지 있어요. 첫째, 훅은 조용히 실패해요. 카탈로그가 망가져도, 정규식이 틀려도, 내부 오류가 나도 세션은 안 깨져요. 둘째, 같은 선택의 뒷면이 fail-open이에요. 훅이 아예 못 도는 상황 — PATH에 `node`가 없거나, 카탈로그를 못 읽거나 — 에서는 `block` 규칙도 같이 안 걸려요. 그러니 차단은 실수를 걸러주는 가드레일로 쓰시고, 뚫리지 않는 샌드박스로 믿지는 마세요.

시작은 [`rules/ballast.rules.example.json`](rules/ballast.rules.example.json)을 복사하거나, **pin**에게 맡기세요. 검증에 두 번째 모델을 세우고 싶으면 [`rules/ballast.verifier.example.json`](rules/ballast.verifier.example.json)을 `.claude/ballast.verifier.json`으로 복사하고, `command`에 주장을 반박해 줄 CLI 아무거나 지정하세요. verify-gate 스킬이 그걸 실행해서 반박을 견줘본 뒤에야 `confirmed`를 붙여요.

Claude가 굴려온 저장소에서 처음 푸시하기 전에는 [docs/PUBLISH-CHECKLIST.md](docs/PUBLISH-CHECKLIST.md)를 한 줄씩 밟으세요 — 이런 작업 공간에는 어느새 안 들여다보게 된 파일들에 비밀값이 쌓여요.

## 철학

긴 Claude 세션이 어긋날 때 보통의 원인은 능력 부족이 아니라 기억과 과신이라는 것 — 이게 ballast의 전제예요. 그래서 규칙은 파일에 두고, 필요한 메시지와 함께 도착하게 해요. 결정은 조용히 고쳐 쓸 수 없는 원장에 남겨요. 주장은 `confirmed`를 얻기 전까지 라벨을 달고 다녀요.

그 라벨 기준으로, 이 README가 밝혀둘 것이 두 가지 있어요. 실적은 `hearsay`(전언)예요. ballast가 생긴 이유는, 개발 배경이 없는 한 사람이 업무 전체를 Claude Code로 돌리면서 그 결과를 믿을 수 있어야 했기 때문이에요. 하지만 그 몇 달의 일상 사용은 비공개 회사 작업 공간에서 있었고, 이 공개 저장소는 2026년 8월에 시작됐어요. 그래서 여기에는 열어볼 수 있는 이력이 없어요. 대신 장치는 확인할 수 있어요. 훅, 스킬 여섯 개, 규칙 형식이 전부 이 저장소에 있고, 한나절이면 다 읽혀요. 새로움 주장은 `unknown`(모름)이에요. 프롬프트 제출 시점에 컨텍스트를 주입하는 건 문서화된 Claude Code 훅 패턴이고, 덧붙이기만 하는 기록은 소프트웨어보다 훨씬 오래된 방식이에요. ballast가 말할 수 있는 최대치는 "이 루프 전체를 묶어놓은 걸 다른 데서는 못 봤다"까지예요. 루프의 선례를 아시면 이슈로 알려주세요. 링크해 둘게요.
